### 2026-07-02 (pre-send email review modal)
- **Statement emails can now be reviewed and edited BEFORE anything is recorded.** Motivated by a real case: an underpaying client's email needed a custom note, but EdgeCase had already written the templated text into the Communication entry, forcing a manual paste-back to keep the record accurate. Clicking Send now opens a review modal (recipient shown, subject and body editable); the approved text is used verbatim for both the outgoing email (AppleScript or mailto) and the Communication entry — the client file always matches what was actually sent.
- **Send is now truly two-phase.** A new read-only `GET /statements/email-preview/<portion_id>` route composes the email with no side effects (no PDF, no Communication entry, portion stays `ready`); `mark-sent` accepts optional `{subject, body}` overrides and does all the recording. This also fixes a pre-existing wart: previously, clicking Send marked the portion sent and created the Communication entry even if the user then abandoned the Mail draft — Cancel in the modal now genuinely aborts. The recipient/template composition was extracted into shared helpers (`_load_portion_and_profile`, `_compose_statement_email`) used by both routes so preview and send can never drift. Generate-only (`skip_email=1`) and older callers posting no body are unchanged.
- 2 new tests: the preview route composes correctly and changes nothing (plus 404 on unknown portion), and mark-sent with edits stores the edited body verbatim in the Communication entry and echoes it to the frontend. Suite 221 → 223, `ruff check` clean.

### 2026-07-01 (client-file balance summary)
- **The client file header now shows two at-a-glance financial figures: Unbilled and Outstanding.** Motivated by a real case — a client paid before being invoiced, and verifying the amount meant manually counting sessions on the profile (which got the wrong number, because "sessions × rate" isn't how the total is computed — per-client fees, consultations, items, and tax all differ). **Unbilled** is what a statement would bill right now; **Outstanding** is what's still owing on statements already sent. Kept deliberately as two separate figures since a client can have both.
- **No new money math.** `get_unbilled_total(client_id)` reuses the statement generator's exact `find_unbilled` predicate and fee resolution (locked, unbilled session/absence/item entries; excludes consultations, pro bono, zero-fee; items fall back to base_price, absences to base_fee), scoped to one client with no date bound — so the number equals what generating a statement would actually pick up. Unlike the bulk generation picker it does *not* exclude Inactive clients (on an individual file you still want to see what they owe). `get_outstanding_balance(client_id)` sums `amount_due − amount_paid` over non-paid/non-written-off portions via the `core/money` Decimal helpers. Both live in `ClientMixin` (`core/db/clients.py`).
- **Guardian-billed minors:** the unbilled figure is the full amount; the header notes it "splits across guardians on statement" rather than implying a single payer. The note uses the same condition the generator uses to create guardian portions (`is_minor` AND `guardian1_name`), so it never appears for a client who has aged out of guardian billing but still has a guardian name on the profile. Zero balances render muted so a real number stands out. Client-file only (one cheap query per file view; deliberately *not* added to the main client list, which would reintroduce the home-page N+1).
- Added `TestClientBalances` (10 tests covering the exclusions, the base_price/base_fee fallbacks, and partial/paid/written-off handling); suite 201 → 211, `ruff check` clean.

### 2026-06-14 (crypto v2 — first-migration fixes)
Three gaps surfaced and were fixed when the first real install migrated to v2:
- **Backups now include `.keyinfo`.** `get_all_backup_files()` captured `.salt`/`.secret_key` but not `.keyinfo`; on a v2 install the raw SQLCipher key is derived from the Argon2id salt inside it, so a backup without it would restore an unopenable database (also a prerequisite for the password-change rollback).
- **Backup verification keys the database copy with the raw key on v2.** `_verify_zipped_database()` opened the backed-up `edgecase.db` with the passphrase, which on a raw-keyed v2 database fails as "file is not a database" and discards the backup. It now mirrors `core.database`: the raw Argon2id-derived key when `.keyinfo` exists, the passphrase otherwise. Covers full, incremental, and pre-restore backups.
- **`core.encryption` reads and writes v2 files.** `decrypt_file_to_bytes()`/`encrypt_file()` were pure Fernet, so after migration every attachment, logo, signature, and statement PDF was unreadable and new files were written as v1. They now dispatch on the `0x02` prefix (v2 → Argon2id-derived file key via `encryption_v2.get_keys`, else Fernet) and write v2 when `.keyinfo` exists, fixing all callers at once. Leftover v1 files stay readable on a v2 install; v1 installs are unchanged.
7 tests across the three fixes; full suite 121 passed. A repo-wide scan confirmed no other v1 assumptions remain in normal operation — the only passphrase-only code left is the manual maintenance scripts `tools/audit_orphans.py` and `tools/audit_typed_columns.py`.

### 2026-06-14 (crypto v2 — password change, Stage 5)
- **The master-password change is now v2-aware.** On a migrated (v2) install, `change_password_progress` runs `migrate_crypto.change_password()`: it derives the old keys from the current `.keyinfo`, derives fresh keys from the new password under a new salt, takes a full backup, re-encrypts every file from the old file key to the new one (atomic per file), rebuilds the database under the new raw key as a separate verified file, and commits by swapping it in and writing the new `.keyinfo`. It reuses the migration's crash-safe machinery: a `.v2_migrating` marker (kind `rekey_v2`) covers the whole operation, and `recover_if_interrupted()` gained one additive branch — for a `rekey_v2` marker it finalizes vs. rolls back by comparing the on-disk `.keyinfo` salt to the marker's recorded new salt (still password-free; the v1→v2 recovery logic is unchanged). A crashed password change therefore always lands on cleanly-old-password or cleanly-new-password, never locked out. The route closes the live DB handle, runs the rekey, and forces a fresh login; on failure the runner has already rolled back. v1 installs keep the existing Fernet/passphrase flow untouched. 6 new tests (happy path, rollback, both recovery branches; the rollback test confirms the old `.keyinfo` is restored). Full suite: 116 passed.

### 2026-06-14 (crypto v2 — login-flow wiring, Stage 4b)
- **The v1→v2 migration now runs automatically at login.** `recover_if_interrupted()` is called at the top of `login()` (before any DB open; a password-free no-op when nothing is pending). After a successful password check on an existing v1 install, `login()` closes the DB handle, hands the password to a single-use server-side token (never the cookie — mirroring the password-change handoff), and renders an `upgrading.html` interstitial. That page opens an SSE connection to the new `/auth/migrate/stream` route, which runs `migrate_crypto.migrate()` (full backup → re-encrypt → rekey → commit, all crash-safe) then opens the now-v2 database, stores it, calls `init_all_blueprints`, and completes the login exactly as the normal path does. The stream route is in `require_login`'s allowed endpoints (it runs while `config['db']` is intentionally unset, gated by the token). On failure the runner has already rolled back to v1 and the page says so. First-run installs are created on v1 as before and migrate on their next login. 5 wiring tests (handoff single-use/expiry/bad-token; stream reachable-without-DB + tokenless error; login still renders). Full suite: 110 passed.
- **Caveat:** the change-password flow is not yet v2-aware (Stage 5). It assumes Fernet files + passphrase rekey, so it must not be used on a migrated install until Stage 5 lands.

### 2026-06-14 (crypto v2 — migration runner, Stage 4a)
- **`core/migrate_crypto.py`: the in-place v1→v2 migration runner**, with a crash-safe state machine — built and tested, but imported by no production path yet (wiring into the login flow is Stage 4b). Sequence: full verified backup (reuses `utils.backup`) → write a `.v2_migrating` marker → re-encrypt every v1 file in place (atomic per file, resumable via content-sniff) → build and verify the raw-keyed DB as a *separate* file (`integrity_check` + row-count parity, original untouched until it passes) → commit (atomic DB swap, clear stale WAL, then write `.keyinfo` as the commit point) → drop the marker. `recover_if_interrupted()` runs at startup needing no password: `.keyinfo` is written only after the DB swap, so its presence proves the migration reached commit (→ finalize), and its absence with a marker present means an interrupted run (→ roll back to the backup). No crash window can leave the user locked out — the result is always fully-v2 or cleanly-v1. The runner only touches files the backup also covers (all attachments + assets logo/signature), so rollback can always restore anything it changed. 5 tests: happy path, immediate rollback on failure, recovery-finalize, recovery-rollback, and detection; fast-KDF fixture keeps them quick. Full suite: 105 passed.

### 2026-06-14 (attachment crypto v2 — primitives)
- **New v2 encryption module (`core/encryption_v2.py`), not yet wired into any production path.** First step of migrating attachment/asset/statement-PDF encryption from Fernet (PBKDF2-SHA256 / AES-128) to an Argon2id → HKDF → AES-256-GCM scheme matching MailRepo's design — using `argon2-cffi` for the Argon2id KDF (matching MailRepo; `cryptography`'s own Argon2id measured ~5× slower on the M4 — ~3.9s vs ~0.74s for identical params), with `cryptography` retained for HKDF/AES-GCM. Argon2id (256 MiB, t=6, p=1) derives a 32-byte master key; HKDF-Expand with domain-separated labels splits it into a raw SQLCipher DB key (for `PRAGMA key = "x'…'"`) and a file key. Files use wire format `[0x02][12-byte nonce][ciphertext+tag]` with the version byte bound into the GCM AAD. v1 Fernet tokens (urlsafe-base64, leading `g` / `0x67` on disk) and v2 blobs (`0x02` prefix) are unambiguously distinguishable, so both stay readable during migration. A versioned key-info file (`.keyinfo`: magic + Argon2id salt + verification token) is written alongside the existing `.salt`, which is left untouched so v1 files remain decryptable through the bake period. 16 unit tests added (round-trip across sizes incl. empty, version dispatch, wrong-key and tamper rejection, KDF determinism and salt-sensitivity, subkey domain separation, key-info round-trip and bad-magic). Full suite: 99 passed.

### 2026-06-10 (locked-entry audit coherence)
- **Unsaved-changes protection on the session form (all modes)**: there was previously no guard at all — navigating away from a half-written session note via Cancel or Prev/Next lost it silently. Dirty state (snapshot comparison, see below) now gates in-app navigation with a custom Unsaved Changes modal (Stay Here / Leave Without Saving). Root cause of a long misfire chase: base.html's server-disconnect handler intercepts every same-origin link click in the document capture phase and navigates programmatically, so a bubble-phase guard could open the modal but never stop the navigation — the (interim) beforeunload warning was the only thing halting the page, surfacing as a native dialog stacked on the modal in every browser. The guard now runs in the window capture phase and stops propagation when dirty, so the disconnect handler never starts; clean clicks keep the normal liveness-checked navigation. Verified in a jsdom harness running the real rendered page including base.html's inline scripts. No tab-close/reload warning is registered (deliberate; the modal covers the in-app loss paths).
- **Fix: dirty detection bound the wrong form on edit pages.** The first cut selected `form[method="post"]`, but edit-mode pages render a second POST form first (the redact button component; HTML matches `method` case-insensitively), so dirty detection silently never fired on saved/locked sessions — exactly the pages that need it most. The entry form now has `id="session-entry-form"` and is selected by id.
- **Cancel relabelled "Back" on locked entries**: when reviewing a locked session there's nothing to cancel; the label now reflects that. New entries and drafts keep "Cancel".
- **No-change saves of locked sessions are now true no-ops**: clicking "Save Changes" on a locked session with no edits previously wrote nothing to the amendment history (already correctly guarded) but still bumped `modified_at` — leaving the record asserting a modification the amendment trail doesn't show. The route now returns without writing when the change set is empty.
- **"Save Changes" on locked sessions is disabled until the form is edited**: the button reads "No Changes" and activates when the form state actually differs from what was loaded (snapshot comparison in `session.js`, since the date/time pickers write values without firing events; restoring a field to its original value re-disables it). UI polish on top of the backend guard, not a substitute for it.

### 2026-06-09 (request-layer security)
- **Per-client session authentication enforced**: `require_login` previously gated only on the app-global unlocked database — `session['authenticated']` was set at login but never checked, so any cookieless request (another device in LAN mode, or any local process) had full access the moment anyone was logged in anywhere. The session marker is now required; each browser/device must present the master password to get its own session. Login already re-verifies the password by opening the database with it, so no change was needed there.
- **Host-header validation (DNS rebinding protection)**: localhost binding alone doesn't stop a malicious web page from rebinding its domain to 127.0.0.1 and making what the browser then treats as same-origin requests — which also bypassed the CSRF JSON exemption's safety rationale. A new first-in-line `before_request` rejects (403) any request whose Host isn't localhost/127.0.0.1/::1; LAN mode (`EDGECASE_LAN=1`) additionally admits private-range and Tailscale CGNAT (100.64/10) IP literals but never DNS names; `EDGECASE_ALLOWED_HOSTS` (comma-separated) covers e.g. Tailscale MagicDNS hostnames. Applies to every endpoint including login and static files.
- **LAN mode plaintext warning**: starting with `--lan` now prints a prominent warning that LAN mode serves unencrypted HTTP (master password and PHI cross the network in plaintext) and recommends Tailscale/SSH tunneling over localhost instead. `--lan` also now sets `EDGECASE_LAN=1` so the Host-validation layer sees one canonical signal.
- **AI model download integrity**: pinned the official SHA-256 of the Hermes 3 Q4_K_M GGUF (verified independently against HuggingFace's LFS metadata and a local copy). Both download paths verify before accepting the file — the blueprint's streaming download hashes incrementally during the stream (no second pass over ~5GB), and `download_model` hashes after `hf_hub_download`. Mismatches are deleted with a clear error.
- **`scribe_save` hardened against malformed JSON**: a request body of JSON `null` (or non-object) previously crashed with an AttributeError → 500; now returns a clean 400.
- **First request-layer tests**: 7 new tests exercise the Flask app via the test client (rebound-Host rejection incl. on the login page, localhost allowance, LAN-mode host rules, cookieless requests rejected while the DB is unlocked, JSON 401 for cookieless API calls, authenticated session passes). 77 tests total.
