Format: Each entry includes date, version (if applicable), and description.

## [Unreleased]

### 2026-08-16 (the suite stops paying the Argon2 tax — nothing about the app itself changed; production strength unchanged and pinned)
- **One central KDF switch instead of six local patches.** `encryption_v2.argon2_parameters()` (ported from Daybook via MailRepo `596e4e8`) feeds every derivation: production strength (256 MiB / t=6 / p=1) everywhere, cheap (1 MiB / t=1 — still real Argon2id, same call site, nothing mocked) only when `EDGECASE_FAST_KDF` **and** `EDGECASE_DATA` are both set. Verified before building, not assumed: neither ECC2 (`magic+salt+token`) nor ECC3 (`magic+salts+wraps`, fixed 190 bytes) records the Argon2 parameters, so an install created cheaply cannot open at production strength — which is why the cheap path takes two variables, and why each alone must do nothing. A real install sets neither; the testing instance sets only `EDGECASE_DATA`.
- **`derive_master` loses its per-call overrides.** Nothing legitimate ever passed them; six test files carried their own copies of the cheap numbers (five swallow-`**kw` lambdas plus a `CHEAP` dict), each one capable of silently shadowing a central switch. All removed; conftest now sets both variables before any project import — overriding `EDGECASE_DATA` unconditionally to a fresh tmp dir, so a suite run from the testing instance's shell can never write into its data — which config-sandboxes the entire suite as a side effect.
- **`tests/test_kdf_cost.py` pins what the cheap path stops proving:** the production numbers as literals (`256*1024` / `6` / `1`, so a typo can't make both sets agree), flag-alone and sandbox-alone both staying at production, params-not-in-keyfile for both formats, and one full-cost v3 round trip under both credentials with a >0.25s floor on the password unlock (the recovery-key KEK is HKDF — deliberately cheap always — so it gets correctness, not a floor). Sealing mutations run and reverted: a constant typo trips the pinned literal, a flag-only switch trips sandbox-alone, and cheap-always trips the floor plus three switch guards — the whole file finishing in 0.03s under that mutation, which is exactly the silent failure the floor exists to catch.
- Measured on the M4: 633 tests in 35.9s before, 642 in 26.6s after — the modest ~26% matching EdgeCase's smaller exposure (most crypto files already patched locally; `test_restore_credentials.py` alone went 10.3s → ~1s). Navigation Map's test counts refreshed (they still said 201).

### 2026-08-16 (restoring a backup you can no longer open is named before it happens, and survivable after)
- **The brick, found in Daybook:** a backup carries its key material as it stood, so a restored practice opens with the master password (and recovery key) of the moment the backup was TAKEN. EdgeCase said nothing about this at the point of restore beyond one generic modal sentence, and nothing on the login screen after — the restore-completed message only fired *after* a successful login, which is exactly the step a locked-out user cannot take. A correct restore was indistinguishable from a rejected password, and restoring a backup with lost credentials was a lockout with the new disaster-recovery routes dead behind it (a database now existed).
- **Prevention (Daybook's fix, mechanics shared with MailRepo): credential fingerprinting.** The ECC3 key-info is two independent halves — (salt_pw + wrapped_pw) and (salt_rk + wrapped_rk) — and every rewrap mints a fresh salt and touches exactly one half, so hashing the halves separately says which credential changed since a backup *without trying a single password*. Every restore point everywhere now carries `credential_status`/`credential_note` (annotated once in `build_restore_points`, so the authenticated API and the recovery scan get it for free): "your master password has changed since this backup — it opens with the one you used then; your recovery key still works", "both have changed — if you have neither, do not restore this one", and the disaster-case note when there is no live key to compare against. Notes render beside each point on the recovery screen, inside its confirm dialog, and in the authenticated restore modal. EdgeCase divergence from MailRepo, deliberate: v1-era backups (salt, no keyinfo) are *not* "obsolete crypto" here — login auto-upgrades them — so they get "opens with the password of the day; predates recovery keys" instead of "cannot be opened".
- **The login screen now says it** (Daybook's unlock-screen ruling): after a restore restart, login shows the restored date and the credential note chosen with the restore point — `complete_restore` carries the note out of the staging marker, and the banner survives failed attempts, which is precisely when it is needed. Peeked from `RESTORE_COMPLETED`, not popped; the post-login code still owns consuming it.
- **The way back (EdgeCase first — neither sibling has it): restores are UNVERIFIED until proven open.** `complete_restore` drops a `.restore_unverified` marker in DATA_DIR (explicitly not in the backup file set); while it stands, the disaster-recovery routes stay open even though a database exists, and the login banner offers "Restore a different backup — including the safety backup of what was here before." The first successful login deletes the marker, which is what closes the door — so a practice in normal use, which by definition has logged in since its last restore, is never reachable this way. This closes the loop the warning alone cannot: in the total-loss case there is no live key to fingerprint against, and "opens with the password of the day" is a claim the user can only test by restoring.
- 25 tests in `tests/test_restore_credentials.py` (fingerprint halves move independently, chain last-keyinfo-wins, every note branch, marker roundtrip, door reopens/closes, login clears the marker, banner renders), all verified to fail against the previous code. `bare_client` moved to conftest, which also gains global isolation for the marker — it is deleted on every successful login, so an unisolated auth test would silently unlink the real install's. 633 passing.

### 2026-08-15 (disaster recovery: a way back in when the database is gone)
- **A missing database no longer dead-ends at "create a new password."** Before this, `is_first_run()` was just `not db_path.exists()`, so catastrophic data loss rendered the first-run screen and typing a password built a fresh, empty practice — while every restore endpoint sat behind login, unreachable by exactly the person they exist for. Found in Daybook, which shares the pattern; the fix is MailRepo's disaster-recovery design ported back to its parent.
- **Five public routes** (`/restore` page plus `/restore/search`, `/scan`, `/browse`, `/prepare`) let someone with no database stage a restore from a backup folder. Public deliberately, for the same reason `auth.login` is; three things keep it narrow: the routes are dead the moment a database exists (`is_first_run()` false → redirect/403, so this is never a way to roll a live practice back over its owner), every POST requires a recovery CSRF token, and completing a restore grants no access — the restored data is still encrypted under the master password in force when the backup was taken. `/prepare` re-scans server-side rather than trusting client-supplied ids or paths, and staging is finished by the existing `complete_restore()` at next startup.
- **Backups are now discoverable without the local manifest.** `save_manifest` stamps every manifest with `"app": "edgecase"` and mirrors a sidecar copy into every custom backup destination, making each folder a self-describing unit; `record_backup_location` notes every destination in a file *outside* DATA_ROOT (`core.config.get_state_dir`: `~/Library/Preferences/EdgeCase` on macOS), so it survives the loss that makes it necessary. Recovery reads the record first, EdgeCase's own default folder second, and a folder picker covers everything else — no disk-sweeping guesswork. Folders written before stamping existed are reconstructed from filenames (`reconstruct_manifest_entries`, chronological so two chains never stitch into one), flagged `reconstructed` so the UI says the list is inference, not a record.
- **EdgeCase now refuses MailRepo backup folders**, the mirror image of the guard MailRepo built against EdgeCase: the two apps' backups are byte-identical except for the database filename inside a full zip. Restoring one into the other would overwrite key material while providing no database.
- **Delete-then-recreate bug fixed in restore staging** (found in MailRepo, present here): incremental deletion tombstones were accumulated and applied after all extraction, so a file deleted in incremental N and recreated in N+1 was wrongly removed — delete the practice logo, upload a new one, and the restored practice had none. Deletions now apply per zip, in chain order (`prepare_restore_from_point`, shared by both restore paths). Regression test verified to fail against the previous code.
- **First-run login screen now warns**: "Already had a practice on this computer? … restore from a backup instead. Creating a password here starts an empty practice."
- `get_restore_points` refactored into a reusable `build_restore_points(entries, override_dir=)` so discovery can resolve a recovered folder's files against where the folder *is*, not where it was written. 33 tests in `tests/test_disaster_recovery.py`, all verified to fail against the previous code; conftest gains global isolation for the backup-locations record (it lives outside DATA_ROOT, so the suite's usual path monkeypatching does not cover it). 608 passing.

### 2026-08-14 (restore now puts the key material back)
- **`complete_restore` restores the key files alongside the database.** The backup set has always deliberately included `.salt`, `.secret_key` and `.keyinfo` — there is a dedicated test asserting so — but the restore path only ever replaced the database, WAL, attachments and assets, leaving the *current* key files on disk. Restoring a backup taken before a password change or crypto migration therefore produced an old database sitting under new key material, which cannot be opened; the one operation the key files were backed up for was the one that never used them. Found from the outside: Daybook, auditing its own restore path against its two parents, noticed EdgeCase matched MailRepo on the backup side but not on the restore side (MailRepo restores its key material explicitly).
- **Key state is mirrored, not merged**: a key file absent from the backup is deleted from disk, so restoring a pre-migration (v1) backup onto a migrated install does not leave a stale `.keyinfo` behind — `keyinfo_exists()` would route key derivation down the v2/v3 path for a passphrase-keyed v1 database. The pre-restore safety backup captures the replaced key files, so nothing is lost.
- **`.rk_pending` joins the backup set and is mirrored on restore.** The acknowledgement flag contains no secrets — only the fact that a recovery key was issued and never typed back — and it describes a specific keyinfo. `migrate_crypto` already treats it as key state in its rollback file set; the backup system now agrees, so restoring a backup taken mid-acknowledgement brings the nag back for the keyinfo whose key was never recorded.
- **User-visible consequence, worth a line in any restore documentation:** after restoring, log in with the password that was in effect *when the backup was taken*. Under v3 the master key survives password changes, but the password wrap in the restored keyinfo is the old one.
- Four regression tests in `tests/test_restore_key_material.py`, each verified to fail against the previous code. 574 passing.

### 2026-08-13 (recovery-key verify: an instruction the reader may never have followed)
- **"Put it back wherever you keep it" no longer closes the verify screen.** It now reads "Keep it where it is." The old line assumed the recovery key is a physical object that had been taken out of somewhere in order to be checked. Often it is not: it is a string copied out of a password manager, or read off a sheet that never moved — and telling that reader to put it back describes an act they never performed, which reads as copy written for a different application. The reassurance above it already carries the substance ("your master password and your records are exactly as they were"), so the closing line only needs to end without issuing an instruction that may not apply.
- **Found in Daybook and corrected there first**, where the same sentence had been inherited from this screen and tightened to "Put it back where it was" — which made it worse by adding the implication that the key had been removed. This is the sibling catching up. Noted because the direction of travel is unusual: the borrowing app found the defect in the lender.

### 2026-08-09 (post-review fix: the net-negative rule applies per payer)
- **A negative *guardian portion* no longer slips past the net-negative statement check.** The skip rule below fired on the statement total, but on a guardian split the total can stay positive while one guardian's share nets negative — sessions assigned to guardian 1, a credit item explicitly assigned to guardian 2. That portion was created `ready`, credit application correctly ignored it, and mark-sent's `amount_paid >= amount_due` test (0 ≥ −50) settled it on the spot: money the payer was owed, evaporated with nothing tracking it. Generation now computes the split *before* creating anything and skips the whole statement when any share is negative, reporting it in the same skipped list; the entries stay unbilled until a period whose charges can absorb the credit. The split is computed once and reused at insertion, so the check and the insert cannot disagree. Regression test verified to fail against the previous code.
- Documented in `Architecture_Decisions.md`, alongside a note for any future refund path: `get_client_credit` sums all NULL-portion rows while `consume_credit` spends only positive ones — the two agree today because every writer is constrained positive, and a writer of negative credit rows must reconcile them first.

### 2026-08-09 (payment allocation: one deposit, many statements)
- **A lump-sum payment can now settle several statements.** Carry-forward made statements *present* a balance-forward total while the system continued to *track* open items per statement; the two models disagreed at exactly one moment — when the client paid. A $300 transfer covering a $100 July statement and a $200 August one had to be hand-split and recorded twice, and neither recorded payment matched the amount that actually arrived. Fixed at the moment of payment entry, where the mismatch lives. Design: `docs/Payment_Allocation_Plan.md`.
- **One payment = one ledger entry**, as in QuickBooks / Xero / Sage "Receive Payment": the cash book gets one line for the money that arrived, on the date it arrived, and the new `payment_allocations` sub-ledger carries which statements it settled. The practical reason is CRA review, where every ledger line should map one-to-one onto a bank line without explanation; splitting a deposit for internal convenience creates that work later, under time pressure.
- **`payment_allocations` is additive** — `CREATE TABLE IF NOT EXISTS` in `_initialize_schema()`, no migration runner, no backup gate, nothing like crypto v1→v2→v3. A row is a claim on a ledger entry: `portion_id` set applies the amount to that statement portion, `portion_id` NULL holds it as **credit** on the client's account. `client_id` / `guardian_number` carry the payer scope so a credit can be found without inferring the payer from a description string. Invariant: `SUM(allocations) == entries.total_amount`.
- **Credit is read from explicit NULL-portion rows, never derived** as "total minus allocations". The derivation is correct for entries this system writes but invents money for any legacy entry with no rows at all — a payment from March would have read as a credit sitting on the account.
- **Backfill skips rather than guesses.** Legacy payments carry only `statement_id`, so on a guardian split the portion is recovered from the description the old `mark_paid` wrote ("Client Payment (Guardian 1)"); anything unresolvable is skipped and counted. Idempotent, `NOT EXISTS`-guarded, runs at startup and prints only on the launch that does work. Live run on the testing instance: 7 created, 0 skipped, no FK violations.
- **`prorata_tax` is computed per allocation, not once on the payment total** — two statements settled by one payment can carry different tax rates, and a single call against the combined total is silently wrong. Covered by a test where a 13%-HST July statement and a tax-free August one are paid together.
- **Guardian scoping is enforced server-side**, not merely in the UI: an allocation naming another payer's portion, another client's portion, or an unsent (`ready`) statement is rejected before anything is written. Overpayment is never forced onto the last portion — `amount_paid` can no longer exceed `amount_due`.
- **`entries.statement_id` stays populated** for the first statement settled, so every existing reader keeps working; `payment_allocations` is authoritative when present.
- **Guardian credit splits fixed** (found while checking whether credits were issuable at all): the per-line sanity clamp in `split_guardian_amounts` compared with `min()` regardless of sign, so a $100 *charge* split 50/50 but a $100 *credit* went entirely to guardian 1. The clamp now follows the line's sign, and guardian 2's share is no longer floored at zero — once credits exist, a net-negative share is a real position, and flooring it broke the portions-sum-to-total guarantee. Reachable via the item form's documented "Use negative amounts for credits".
- **No statement is generated when a period's credits exceed its charges.** A credit item normally just reduces the period's total, but with too few charges to absorb it the statement total went negative — producing a document telling the client *they* are owed money, and a portion the payment modal refuses to settle (the December 2025 refund branch was written for exactly this case and has never been reachable, since the modal's positive-amount validation predates it by eight days). Generation now skips that client and reports it by name in the result; the entries stay unbilled and carry to the next period that can absorb them. A zero total still generates — it documents the offset and settles the entries. Decided against building a refund path at all: a credit sitting against the next statement is the answer for any continuing client, and a client who insists on cash is rare enough to handle as a manual Ledger expense.
- **The payment modal is now per-payer, and `mark_paid` is gone.** Opening it from any statement row resolves the payer behind that row and lists every open statement for them, oldest first, with a proposed split you can override line by line — "this cheque is for August only" is expressible. Amount and date (custom date picker, defaulting to today) sit above the split; a running summary says what will be applied and what will be held as credit. Changing the amount re-asks the server for a fresh proposal rather than recomputing in JavaScript, so the oldest-first arithmetic exists in exactly one place. Keeping the old per-portion path would have meant two UIs for one operation, and the per-portion path *is* the defect — it records a payment against one statement when the money settled several. The December 2025 refund branch was removed with it (see above).
- **Credit applies itself to the next statement, as an explicit line.** Rendered as `Credit applied  -$50.00` beside "Previous balance", never netted silently into the total. The argument is symmetry: carry-forward already pulls prior *debits* onto the next statement without asking, and making credits wait for the practitioner to remember them is asymmetric in the practitioner's favour — the wrong direction on a clinical bill. Consumption runs on the generation cursor inside the generation transaction, so a credit cannot be spent twice even by two statements generated in the same batch; the second reads a balance the first has already reduced. Credit rows are taken oldest first and reduced in place, and each amount taken becomes an `is_credit` allocation row against the new portion.
- **The originating ledger entry is never rewritten when credit is spent.** The deposit was recorded when it arrived, possibly in a filed period; pro-rated tax goes on the allocation row instead, so the sub-ledger is accurate without altering a reported figure. (Worth a word with an accountant; it is a small change in `consume_credit` if they prefer otherwise.) A test asserts every income entry is byte-identical before and after consumption.
- **A statement fully covered by credit is still issued, then goes straight to `paid` when sent** — the client gets a document showing the credit applied, but nothing is left to collect, and leaving it `sent` would park a $0.00 row in Outstanding Statements with no action that clears it.
- **Client file shows a Credit figure** when one exists, in the practice accent green with the note "credit applies to the next statement", so it doesn't read as a stranded number. Absent entirely when there is no credit.
- **Payment Record prefers allocations.** A lump sum settling several statements carries `statement_id` for only the first of them, so matching on that alone dropped the payment from the record of every other statement it settled; the filter now also matches a `payment_allocations` row for the client. Legacy payments still match by source file number. The refund filter additionally matches the file number as payee, so a hand-entered Ledger expense — the manual path for the rare cash refund — appears on the client's record. 7 SQL-level tests, including that business expenses (rent) stay off a client record and that the date range still bounds it.
- 81 new tests (`test_payment_allocations.py`, `test_record_payment.py`, `test_statement_credits.py`, `test_credit_balances.py`, `test_payment_record_filter.py`, plus credit cases in `TestGuardianSplitRounding`); the two mark-paid lifecycle tests now drive `record-payment`. Suite 481 → 568, `ruff check` clean.

### 2026-08-09 (crypto v3: envelope encryption + recovery keys)
- **Recovery keys.** The master key is now 32 random bytes wrapped twice — once under the password (Argon2id), once under a printed recovery key (HKDF over 160 bits of uniform entropy). Either wrapper yields the same master, so `derive_subkeys` and the v2 attachment wire format are unchanged and nothing below the master knows v3 exists; only the key-info file changes, `ECC2` → `ECC3`. A forgotten master password stops being terminal, which under CRPO's ten-year retention obligation is a professional problem and not merely an inconvenience. Ported from MailRepo's v3 work (2026-08-09).
- **Password changes no longer re-encrypt anything.** Because the master is random rather than password-derived, changing the password is a 190-byte rewrap: no file walk, no DB rebuild, no backup gate, no marker, no rollback window. This is a risk reduction, not just a feature — it removes an entire failure surface from an operation performed on live clinical records.
- **Single-pass migration from v1 *or* v2.** `migrate_to_v3()` goes straight to v3 rather than chaining through v2, so a v1 install gets one file walk and one DB rebuild instead of two. Reuses `_reencrypt_file`, `_reencrypt_file_v2`, `_export_verify`, `_rollback` and the marker machinery unchanged; only the two "old key" resolutions differ. No resume-state file (which MailRepo needs for its in-place `PRAGMA rekey`): the rebuilt DB is a separate verified file, so rollback-to-known-good is available and is the stronger guarantee.
- **`keyinfo_exists()` keeps meaning "not v1"**, so seven of eight call sites are untouched; `get_keys()` is the single chokepoint that sniffs the magic, and `keyinfo_version()` serves the three places that genuinely branch. Contract change: under v3 a wrong password raises rather than returning garbage keys, since the wrapper's GCM tag *is* the verification (ECC3 has no separate token). `Database.verify_password` is the only caller passing unverified input.
- **Recovery door**: `/recover` opens the install with the key and resets the password. Rate-limited with `/login`; a *malformed* key does not spend an attempt (a typo is not a guess, and burning the lockout budget on mistyping 32 characters would make the door useless exactly when needed). Does not auto-login — the user has typed the new password exactly twice, so using it once more is the cheapest confirmation it is what they think it is.
- **Non-destructive verification** (Settings → Security → *Check My Recovery Key*): unwraps, reports, writes nothing. Added after comparing against MailRepo, whose recovery unlock is non-destructive; EdgeCase's reset model meant testing a key cost you your password, punishing exactly the person prudent enough to check. Copying MailRepo directly is not available — its master lives in class state, whereas EdgeCase threads the password through `Database(password=...)`, `_key_cache` and the session — so verification covers the same need without a second unlock mode through the auth layer. `/recover/reset` now also warns before committing, for the remembered-it-halfway case.
- **Deliberate asymmetry**: a password change revokes the old password; using a recovery key does *not* revoke the recovery key. If a key has leaked, an attacker who used it must not be able to rotate it and lock the real owner out permanently.
- **`_key_cache.clear()` is load-bearing on the v3 rewrap paths**, not hygiene. The derived keys are identical either side of a password change, so a stale entry under the old password string would keep handing out working keys until restart — a revoked password that still opens the install, with the on-disk crypto entirely correct. Covered by a dedicated test.
- **`.rk_pending`** records that a key was issued but never acknowledged — never the key itself. Written *before* the commit point, and deliberately survives the `recover_if_interrupted` finalize path. Drives a persistent banner (fails closed) rather than a one-shot modal. This earned its keep on the first live run: a `url_for` inside the SSE generator raised *after* the migration committed, the key was discarded with the exception, and the flag carried the state forward.
- **Acknowledgement is a checkbox, not a typed key** (revised after Rick flagged the incoherence). Typing it back looked stronger than it was — the same page offers Copy to clipboard, so paste satisfied the check with the key never reaching anything durable — and the adjacent "I'll do this later" link read as a peer choice. Now matches MailRepo: one checkbox, Continue disabled until ticked, no escape hatch on the page, validated server-side. Copy / Download as .txt / Print ported from MailRepo's `recovery-key.js`.
- **Packaging manifest fixed and alarmed.** `setup_app.py` had accumulated three refactors' worth of gaps: the `core/db/` mixins, both blueprint packages, the crypto modules, and `argon2` — which, imported only inside `encryption_v2` and being a CFFI extension, would have failed at *login* in a packaged build that otherwise looked fine. First-party code is now declared as packages rather than an enumerated module list; `test_packaging_manifest.py` asserts the manifest still describes the running app (verified to fail when a package is removed).
- **Bugs found by testing, not by tests**: `url_for` inside the SSE generator (Flask pops the app context before the generator runs); an error handler that claimed "your data is unchanged" on *any* exception, including ones raised after commit; four new forms with no CSRF token (the test client does not enforce CSRF — now covered by a test that walks every template); and a regenerate route reachable only from the pending banner, so it vanished once a key was acknowledged.
- 138 new tests across `test_encryption_v3.py`, `test_migrate_v3.py`, `test_recovery_key_routes.py`, `test_csrf_tokens.py` and `test_packaging_manifest.py`, including both upgrade paths to an openable v3 with attachments verified byte-identical, crash injection at every phase rolling back to a clean openable original, and password-free recovery either side of the commit point. Suite 242 → 454, `ruff check` clean.
- `tools/reset_test_data.sh` added: restores the testing data directory from a pre-upgrade snapshot by *moving aside*, never deleting, and refuses to run against production, a non-testing path, a non-EdgeCase directory, a post-upgrade snapshot, or while a server holds port 8080.
- **Verified end-to-end on the testing instance** (2026-08-09): upgrade from ECC2, key display and download, checkbox acknowledgement, attachments, statement PDF with logo (the `assets/` half of the rekey), AI Scribe, recovery-key login and password reset, regeneration from Settings, non-destructive verification, and revocation of both the old password and the old recovery key.

### 2026-06-14 (crypto v2 — first-migration fixes)
Three gaps surfaced and were fixed when the first real install migrated to v2:
- **Backups now include `.keyinfo`.** `get_all_backup_files()` captured `.salt`/`.secret_key` but not `.keyinfo`; on a v2 install the raw SQLCipher key is derived from the Argon2id salt inside it, so a backup without it would restore an unopenable database (also a prerequisite for the password-change rollback).

They now dispatch on the `0x02` prefix (v2 → Argon2id-derived file key via `encryption_v2.get_keys`, else Fernet) and write v2 when `.keyinfo` exists, fixing all callers at once. Leftover v1 files stay readable on a v2 install; v1 installs are unchanged.

### 2026-06-14 (crypto v2 — password change, Stage 5)

The route closes the live DB handle, runs the rekey, and forces a fresh login; on failure the runner has already rolled back. v1 installs keep the existing Fernet/passphrase flow untouched. 6 new tests (happy path, rollback, both recovery branches; the rollback test confirms the old `.keyinfo` is restored). Password read via getpass (never an argument). Validated on real data: 39 files migrated, 364 rows preserved across 13 tables, integrity_check ok, Argon2id derive 0.74s, PASS.
- **`database.py` now keys SQLCipher with the raw v2 key when a `.keyinfo` file is present.** It derives the key (Argon2id → HKDF, cached per password so the ~0.74s derive runs once, not per connection) and opens with `PRAGMA key = "x'…'"`. With no `.keyinfo`, the passphrase path runs exactly as before, so un-migrated (v1) installs are wholly unaffected — verified by the full suite still passing. `verify_password` checks the key-info verification token for v2 installs (no database open needed). New test opens a real raw-keyed database through `Database` and confirms the passphrase no longer opens it. Full suite: 100 passed.

### 2026-06-14 (attachment crypto v2 — primitives)
- **New v2 encryption module (`core/encryption_v2.py`), not yet wired into any production path.** First step of migrating attachment/asset/statement-PDF encryption from Fernet (PBKDF2-SHA256 / AES-128) to an Argon2id → HKDF → AES-256-GCM scheme matching MailRepo's design — using `argon2-cffi` for the Argon2id KDF (matching MailRepo; `cryptography`'s own Argon2id measured ~5× slower on the M4 — ~3.9s vs ~0.74s for identical params), with `cryptography` retained for HKDF/AES-GCM. Argon2id (256 MiB, t=6, p=1) derives a 32-byte master key; HKDF-Expand with domain-separated labels splits it into a raw SQLCipher DB key (for `PRAGMA key = "x'…'"`) and a file key. Files use wire format `[0x02][12-byte nonce][ciphertext+tag]` with the version byte bound into the GCM AAD. v1 Fernet tokens (urlsafe-base64, leading `g` / `0x67` on disk) and v2 blobs (`0x02` prefix) are unambiguously distinguishable, so both stay readable during migration. A versioned key-info file (`.keyinfo`: magic + Argon2id salt + verification token) is written alongside the existing `.salt`, which is left untouched so v1 files remain decryptable through the bake period. 16 unit tests added (round-trip across sizes incl. empty, version dispatch, wrong-key and tamper rejection, KDF determinism and salt-sensitivity, subkey domain separation, key-info round-trip and bad-magic). Full suite: 99 passed.

### 2026-06-10 (locked-entry audit coherence)

### 2026-06-09 (request-layer security)
- **Per-client session authentication enforced**: `require_login` previously gated only on the app-global unlocked database — `session['authenticated']` was set at login but never checked, so any cookieless request (another device in LAN mode, or any local process) had full access the moment anyone was logged in anywhere. The session marker is now required; each browser/device must present the master password to get its own session. Login already re-verifies the password by opening the database with it, so no change was needed there.
- **Host-header validation (DNS rebinding protection)**: localhost binding alone doesn't stop a malicious web page from rebinding its domain to 127.0.0.1 and making what the browser then treats as same-origin requests — which also bypassed the CSRF JSON exemption's safety rationale. A new first-in-line `before_request` rejects (403) any request whose Host isn't localhost/127.0.0.1/::1; LAN mode (`EDGECASE_LAN=1`) additionally admits private-range and Tailscale CGNAT (100.64/10) IP literals but never DNS names; `EDGECASE_ALLOWED_HOSTS` (comma-separated) covers e.g. Tailscale MagicDNS hostnames. Applies to every endpoint including login and static files.
- **LAN mode plaintext warning**: starting with `--lan` now prints a prominent warning that LAN mode serves unencrypted HTTP (master password and PHI cross the network in plaintext) and recommends Tailscale/SSH tunneling over localhost instead. `--lan` also now sets `EDGECASE_LAN=1` so the Host-validation layer sees one canonical signal.
- **AI model download integrity**: pinned the official SHA-256 of the Hermes 3 Q4_K_M GGUF (verified independently against HuggingFace's LFS metadata and a local copy). Both download paths verify before accepting the file — the blueprint's streaming download hashes incrementally during the stream (no second pass over ~5GB), and `download_model` hashes after `hf_hub_download`. Mismatches are deleted with a clear error.
- **`scribe_save` hardened against malformed JSON**: a request body of JSON `null` (or non-object) previously crashed with an AttributeError → 500; now returns a clean 400.
- **First request-layer tests**: 7 new tests exercise the Flask app via the test client (rebound-Host rejection incl. on the login page, localhost allowance, LAN-mode host rules, cookieless requests rejected while the DB is unlocked, JSON 401 for cookieless API calls, authenticated session passes). 77 tests total.
